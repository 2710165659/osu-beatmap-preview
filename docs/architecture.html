01

系统架构总览

从 CLI / Rust API 进入，经由单一编排服务完成下载、解析、转谱、渲染和输出；四种游戏模式共享领域模型与底层画布，视频路径额外接入音频和编码器。

CONTROL POINT

服务编排是唯一主入口

所有格式都由 `pipeline::service::generate_preview` 统一控制截止时间、缓存、目标模式和输出元数据。

SHARED CORE

模型与画布复用

`Beatmap`、`HitObjects`、`Img`、时间轴和通用转换逻辑在模式之间共享，模式 renderer 只负责差异化布局。

MEDIA EDGE

MP4 是额外分支

只有 MP4 启动 OSZ 音频 / 背景工作，并根据平台尝试 NVENC、AMF，最后回退到 OpenH264。

02

端到端处理流程

一条请求从参数进入到 stdout JSON 返回的阶段框架。实线表示必须完成的主流程，虚线表示缓存命中、可选转谱或 MP4 专属并行工作。

03

请求时序

以一次 MP4 请求为例，强调服务层如何串联外部下载、解析和模式 renderer，并让音频工作与视频帧处理并行，最后按顺序 mux。

04

模块依赖

按 Rust crate 内部边界抽象，而不是逐文件展开。fan-in 数字表示下游模块使用该模块的数量，突出 `core/models`、`render/canvas` 和 `pipeline/service` 这些共享节点。

05

部署 / 运行时视图

程序是单文件跨平台 CLI / library；运行时主要落在本机进程与临时目录，网络边界只承担谱面和谱面集资源获取。Windows 下硬件编码器通过动态加载尝试，不可用时 CPU 回退。

06

核心领域模型

`Beatmap` 是输入域聚合根；解析结果保留 osu! 文件的通用区段，同时用模式化 `HitObjects` 表达 Standard、Taiko、Catch、Mania 四种对象集合。渲染请求和输出是 pipeline 层的外部工作对象。
